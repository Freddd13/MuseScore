# AI怎样读当前谱，以及下一步怎样改

本页保留2026-10-24、0.104.0时的核查与设计。E1标题和E2-V1原生谱图已在0.140／0.141检查，操作见[实际谱图读取](AI_IMAGES_141_GUIDE.md)。E2-C任务资料已在0.143检查，操作见[继续AI编配](AI_TASK_143_GUIDE.md)。当前安装、已准备更新和E2-W后续安排见[当前进度](REWORK_PROGRESS.md)。

## 1. 这次查到了什么

你的观察有依据：当前“显示乐谱”入口会根据音符数据重新画谱，画面与MuseScore会有差异。完整选段读取已经采用原生接口，但旧的文本转换和重新画谱入口仍同时存在，AI可能走到不同路径。

本次核对源码、安装目录中的页面、连接配置和MCP构建记录。六个相关Python文件的校验值与随包构建记录一致，安装的画谱页面也与当前源码一致。还未取得昨天那次调用记录，因此标题究竟在哪一步出现偏差，要在E1用原操作复查。

### 当前连接经过哪里

```text
Codex
  → 随程序附带的 MuseScoreMCP.exe
  → 本机 WebSocket
  → MuseScore 内置连接桥
  → 当前窗口、当前标签页里的内存乐谱
```

Python程序整理工具参数、选段数据和编配任务。Codex负责理解要求和提出写法；MuseScore负责实际读取、排版、播放、采用和撤销。

打开多个MuseScore窗口时，连接窗口选择本次使用的程序；进入该程序后读取当前乐谱标签页。后续要把程序窗口和乐谱标签页的身份一起返回，方便每次核对。

### 当前三个读谱入口

| 入口 | 实际得到什么 | 这次发现的问题 |
|---|---|---|
| `read_arrangement_context` | 分页读取当前内存选段，包含音符、声部、拼写、延音、力度、踏板、反复位置、材料和已有和弦解释 | 适合作为主要入口；标题只读作品信息，谱面标题和布局资料还需补齐 |
| `get_score_data` | 在当前宿主上使用上述分页结果，转成旧的小节／谱表结构 | 转换后的谱表名称使用通用编号，一些丰富信息需要保留原始结果才能看到 |
| `get_score`、`show_score` | 前者把旧读谱数据转成LilyPond文本；后者把旧数据交给VexFlow绘制HTML谱面 | 原生排版、谱号、拍号、连线、文字和净谱细节不能完整对应 |

`show_score`会按平均音高推测高低音谱号，按前两小节起点间距推测拍号，再自行分行；延音线和连音组括号也没有画全。它返回结构数据和一个交互页面，目前没有通过这个工具返回MuseScore原生谱面图片。

### 标题为什么可能对不上

现在有三种内容被界面或工具当成“谱名”：

- AI连接列表显示乐谱的内部名称，通常与文件或标签页有关。
- 原生选段查询读取作品信息里的`workTitle`。
- 旧QML查询读取`workTitle`，后面的`curScore.title`仍指向同一个作品信息字段。

谱面上可编辑的标题文字是另一个对象。它可以与作品信息、文件名分别修改。当前查询没有把这几项分别交代清楚，所以AI仅凭一个`title`字段，无法可靠地解释你看到的标题。

## 2. E1先统一谱的身份和标题

每次读谱先返回一张简短的“当前谱”说明：窗口、标签页、总谱或分谱、可见标题、文件名、是否有未保存修改，以及本次范围。

身份数据保留这些项目：

| 数据 | 用途 |
|---|---|
| 程序实例、乐谱会话、总谱／分谱身份 | 区分多个窗口和标签页，避免在切谱后继续读另一份内容 |
| 文件位置、标签页名称 | 找到用户正在编辑的文件；未保存的新谱也有会话身份 |
| 谱面标题文字列表 | 保留实际文字、标题类型及所在页面，支持多行、不同分谱和没有标题的谱 |
| 作品信息标题 | 与谱面文字并列提供，便于解释差异 |
| 内容版本、演奏版本、排版版本 | 分别判断音符、实际播放数据和图片是否需要更新 |

用于显示的一行名称优先采用当前谱面的标题，其次作品信息、标签页或文件名；返回结果同时写明名称取自哪里。需要识别和修改音符时使用会话与版本引用。

## 3. E2提供“选段数据＋原生谱面图”

保留已有分批读取，补充MuseScore原生绘图能力。一次读取可以同时拿到同一份谱、同一个版本的音符和图片。

### 怎样给AI看图

- 指定第9—12小节，或直接采用当前选区；范围可精确到音符／休止符和谱表、声部。
- 默认沿用当前排版，按谱行裁出目标及必要上下文。保留谱号、调号、拍号、力度和两端连线，目标范围用单独的轻量标识说明。
- 跨谱行时返回几张有顺序的图片，各自标明小节、拍位、页面和谱表；同时可取整行或整页。
- 原生谱面图提供清楚的音符和文字。另有“查看当前编辑显示”选项，用于检查和弦临时标记、范围手柄、编配提示等屏幕内容。
- 图片附带坐标与对象引用的对应关系。AI提到“第二行这个升F”时，可以定位到具体音符；查看图的操作保持当前选音和播放位置。

原生实现可复用现有页面绘制与元素排序，增加范围裁图。当前`savePng`会临时设置打印状态和像素比例，新读取接口需要完整保存、恢复这些状态，结合当前内存布局处理。图与数据准备期间若有修改，则更新对应部分后再返回一组一致结果。

MCP结果直接携带图片内容块，并附结构数据。交互页面复用同一张原生图，点击可定位。这样能同时服务AI读图和用户查看；图像传递方式以[MCP工具结果规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)及[官方Python媒体接口](https://py.sdk.modelcontextprotocol.io/servers/media/)为依据，实施时检查当前Codex实际收到的图片。

### 统一数据组织

沿用已有设计，按用途拆开读取，并用相同的谱、范围和版本关联：

| 部分 | 内容 |
|---|---|
| 当前谱 | 身份、标题、当前选区、各声部和全曲位置概览 |
| 记谱 | 音符、休止、精确时值、拼写、声部、连音组、延音和跨边界关系 |
| 演奏 | 实际起音、松键、力度、速度、踏板及展开反复中的出现位置 |
| 谱面 | 原生图片、页面／谱行、对象位置及坐标换算 |
| 音乐解释 | 和弦、级数、旋律角色、分手和分析理由，保留来源及人工修改 |
| 参考材料 | 录音、取音标注、歌词、参考谱和局部对应关系 |
| 当前任务 | 目标、范围、希望保留的内容、允许改动的内容和少量候选 |

AI按任务读取需要的部分。例如查和弦时先读相邻起音、延音和踏板；修圆滑线时读原生图、实际对象位置和相关曲线；调整演奏时读实际MIDI事件和时间对应。完整数据留在本地，后续查询补充相邻段。

首版扩展现有`read_arrangement_context`，加入按用途选择的数据与原生图；增加按已读版本取图的入口。旧入口保留兼容，并统一到同一个读取服务，工具说明明确主要用途。

## 4. AI怎样完成一次编曲任务

以“保留旋律，让这四小节左手疏一些”为例：

1. 读当前谱说明，核对选中的四小节、谱表和声部。
2. 取得这四小节的数据和原生图，补读前后必要的和声、延音与踏板。已有用户解释、原曲关联按任务一起提供。
3. 比较少量具体写法。需要确认旋律在哪个声部等创作问题时，结合实际谱面询问；已有明确要求直接沿用。
4. 在谱中呈现变化和同处试听，图与差异都标出相应位置。
5. 按用户要求采用或存为另一种写法；一次采用一次撤销，重新读回实际音符、演奏与谱面图。
6. 用户继续改谱后，更新相关范围；当前任务、已确定的解释和参考资料继续保留。

AI可以分别开展分析、写作、演奏和净谱任务，共用这些数据和操作。Python服务继续负责整理与计算，候选生成沿用当前Codex对话。

## 5. 性能和完整操作检查

全曲概览先提供小节、声部、结构位置与可用资料；详细音符和图按段请求。图片按排版版本、范围、分辨率和显示方式缓存，缩放与复看尽量复用；编码、传输和数量设上限，较长范围逐行返回。计算与缓存沿用E盘目录。

测试同时记录读取时间、图片准备时间、传输大小和实际可读性，再确定默认图片尺寸与每次返回数量。

| 编号 | 实施与检查 |
|---|---|
| E1-I | 故意使用三个不同的文件名、作品标题和谱面标题；再检查未保存改名、分谱、多窗口、切标签页、另存和程序目录移动 |
| E2-V | 同一次读取的数据与图对应；覆盖单音、部分小节、跨行、跨谱表、连音组、延音、力度、手工位置和屏幕临时标记 |
| E2-C | 按分析／演奏／净谱任务读取；保留真实谱表名、音高拼写、反复遍次和资料来源；改音与改布局分别检查刷新 |
| E2-W | 用随包exe在实际Codex中走完读取、看图、提出局部写法、看差异、试听、采用、撤销和保存重开 |

验收时保留MuseScore原图、工具实际返回的图和数据，同时核对选音、播放位置、保存状态与撤销次数。昨天标题偏差的原操作在E1复查；这次确认的重新画谱路径作为E2-V的具体修复对象。
