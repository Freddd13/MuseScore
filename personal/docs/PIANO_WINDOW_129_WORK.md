# R1-C3.3-B：钢琴窗口与播放检查

更新：2026-10-27。音源运行方式与声音块记录已包含在 **0.129.0**；本页保留研究过程，当前状态见[安装检查](RELEASE_129_CHECKS.md)。

## 本轮范围

继续追查多谱、和弦、编辑器及滚轮一起使用时的播放与缩放卡顿。自动保存实验已经撤回，保存源码及编译清单与已发布版本一致；本轮继续使用原保存流程。

## 已核对的结果

- Pianoteq 厂商窗口直接运行时，四轮主窗口最长间隔为 50.86、199.39、44.54、88.96 毫秒；独立运行的四轮为 43.62、44.44、38.24、30.90 毫秒。原生消息记录包含 Pianoteq 模块的 JUCE 窗口消息。
- 为已经载入的音源增加“运行方式”选择。Pianoteq、CFX 各自使用本谱音源和共用钢琴，共四种组合，通过控件键盘选择核对了音色、效果、声音、保存重开、撤销重做及切回 SF2。六项通过，166.666 秒。真实鼠标操作仍待检查。
- 播放中切换运行方式后，软件停止在切换时的拍位；再次播放实际发声。单独检查声音线程优先级的设置与恢复。合计四项通过，11.635 秒。
- 为独立声音进程增加缓冲计数，分别记录按时返回、未及时返回、输入占用和处理失败。此前厂商窗口打开的四轮中，播放计数区间共九块声音未及时返回，输入占用及处理失败均为零。
- 尝试采用 Windows 的 Pro Audio 调度。关闭厂商窗口时，四谱八轨组合完成四轮，78.471 秒；主窗口最长间隔分别为 36.79、47.01、49.99、33.05 毫秒。三个音源合计 18,864 块输出，三块未及时返回，输入占用和处理失败均为零。三个遗漏发生在同一轮，仍需检查。

调度使用 [Windows 多媒体任务接口](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)，仅调整独立进程的声音工作线程，离线处理恢复原线程优先级。尚不能用不同窗口条件的两组数字判断调度改动的效果。

## 窗口超时的后续核对

厂商窗口打开的组合检查两次停在独立进程的 `editor` 请求，随后超时。第一轮 113.960 秒，带请求记录的复查 110.406 秒。这两次均未进入正式播放测量。

线程现场两次落在Windows DWrite字体读取中，后一次累计CPU时间约74秒。相同程序在正常权限下通过四轮窗口及播放操作，69.522秒，随后原工作进程与调度尝试各完成四轮相同条件对照。这项超时已定位到受限测试环境的字体读取，相关系统字体保持原样。

原工作进程18,864块输出中五块未及时返回；Pro Audio调度18,891块中六块未及时返回，输入占用与处理失败均为零。调度尝试没有稳定改善，现已退出编译和调用，沿用原声音调度；实验文件保留。原、新主窗口最长间隔分别为37.15／43.03／43.62／37.77毫秒和46.00／38.54／62.17／37.72毫秒。

桌面取点另已确认被Windows LockApp覆盖，正常权限下的鼠标复查也命中同一锁屏窗口，检查因此退出。解锁后继续菜单选择与厂商控件焦点。期间接着C3-A的实际按键数据检查。
